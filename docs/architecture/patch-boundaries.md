## Rules

- RitsuLib patch classes are entry points and should forward into named services.
- New patch surfaces must use RitsuLib `IPatchMethod` / `ModPatcher` registration unless the owner approves a documented exception.
- Patches touching run, room, save, lobby, multiplayer, or lifecycle are release-sensitive.
- Moving or adding a patch requires regenerating `docs/patch-inventory.md`.
- No patch may be used as proof that live UI, save/load, or co-op works.
- **Phase 2 adapter rule:** Every high-risk patch must be a thin adapter. The RitsuLib patch method forwards into a named service method; business logic lives in the service.
- **No same-PR move + behavior change** for any high-risk patch. Move first, verify build/tests pass, then change behavior in a separate PR.
- Forbidden behaviors (see table above) are enforced by source guard tests where possible.

## Phase 2 Patch Adapter Rule — Status: Started / adapter checklist drafted (2026-05-29)

## Review Checklist

- Patch has an owner in `docs/patch-inventory.md`.
- Patch class is registered through RitsuLib `IPatchMethod` / `ModPatcher` and does not add a class-level `[HarmonyPatch]` declaration.
- Patch has a source evidence file if it touches high-risk game APIs.
- Patch delegates to service/state code.
- Tests check the intended boundary.
- Runtime rows remain open until manual evidence exists.
- Every high-risk patch group above has a matching row in `docs/toreview.md` or `docs/issues.md` before user handoff.

## Core Invariants

- `RunState.Rng` and `PlayerRngSet` counters are advanced only by committed game actions.
- `RewardsSetSynchronizer` remains the reward click authority in multiplayer.
- `StartRunLobby.SyncAscensionChange` remains the multiplayer ascension synchronization boundary.
- `NClickableControl` intercepts are narrowly scoped to the intended screen/control type.
- `CombatRoom.ToSerializable` must not see an active non-prefinished child combat with `ParentEventId`.
